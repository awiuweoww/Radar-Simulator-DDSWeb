3. List QoS & Hirarki

Memahami kebijakan Quality of Service (QoS) untuk pengiriman data yang optimal.

QoS Matching: Kunci Komunikasi DDS

Dalam DDS, komunikasi antara publisher dan subscriber tidak akan langsung terjadi begitu saja, tetapi harus melalui proses QoS matching atau kecocokan QoS. Proses ini digunakan untuk memastikan bahwa konfigurasi Quality of Service yang dimiliki oleh publisher dan subscriber saling kompatibel sehingga pertukaran data dapat berlangsung dengan benar.

Jika QoS antara kedua pihak tidak sesuai, maka koneksi komunikasi dapat gagal terbentuk meskipun keduanya berada pada topic yang sama.

Daftar Kebijakan QoS Utama

  • Reliability: RELIABLE (jaminan sampai) vs BEST_EFFORT (cepat, tanpa jaminan).
  • Durability: VOLATILE (data transient) vs TRANSIENT_LOCAL (simpan data untuk subscriber baru).
  • History: KEEP_LAST (simpan N data terakhir) vs KEEP_ALL (simpan semua data).
  • Liveliness: Menentukan kapan sebuah entitas dianggap "mati" atau tidak aktif.
  • Deadline: Batas waktu pengiriman data harus sampai.

Hirarki Pewarisan QoS

QoS dapat diatur di berbagai level entitas. Jika tidak diatur, entitas di bawah akan mewarisi QoS dari entitas di atasnya:

  1. Domain Participant (Global)
  2. Publisher / Subscriber (Grup)
  3. DataWriter / DataReader (Spesifik/Individual)

Tabel Kompatibilitas QoS (Matching)

Tabel berikut merinci aturan kecocokan antara DataWriter (Offered) dan DataReader (Requested) agar komunikasi dapat terjalin:

Nama QoS Jika Writer Mengatur... Maka Reader Harus... Akibat Jika Tidak Cocok
Reliability Menyetel RELIABLE (Pasti sampai) Bisa meminta RELIABLE atau BEST_EFFORT. Jika Reader minta RELIABLE tapi Writer hanya sedia BEST_EFFORT, mereka tidak akan terhubung.
Durability Menyetel TRANSIENT (Simpan data lama) Bisa meminta TRANSIENT atau VOLATILE. Jika Reader minta data disimpan (TRANSIENT) tapi Writer tidak menyimpannya, mereka tidak akan terhubung.
Deadline Menyetel durasi 10 detik (Janji kirim tiap 10s) Harus meminta durasi sama atau lebih lama (misal 10s atau 12s). Jika Reader minta data tiap 5 detik tapi Writer hanya sanggup 10 detik, koneksi gagal.
Ownership Menyetel EXCLUSIVE (Hanya satu pengirim) Harus menyetel EXCLUSIVE juga. Jika satu SHARED dan satu EXCLUSIVE, mereka tidak akan saling bicara.
Liveliness Berjanji lapor diri tiap 5 detik Harus meminta laporan sama atau lebih lama (misal 5s atau 10s). Jika Reader ingin dipantau ketat tapi Writer santai, koneksi gagal.
Presentation Menyetel urutan tingkat GROUP Harus meminta tingkat yang sama atau lebih rendah (misal TOPIC atau INSTANCE). Jika Reader minta aturan lebih ketat dari yang disediakan Writer, data tidak akan mengalir.
Destination Order Menyetel SOURCE_TIMESTAMP Bisa meminta SOURCE atau RECEPTION. Jika Reader minta urutan waktu pengirim tapi Writer tidak menyediakannya, mereka tidak cocok.
Latency Budget Memberi info durasi pengiriman Nilai Writer harus lebih besar atau sama dengan nilai Reader. Digunakan untuk kecocokan asosiasi agar performa sistem tetap terpantau.

Tabel Ketergantungan (Inter-dependencies)

Beberapa kebijakan QoS saling mempengaruhi satu sama lain dalam operasionalnya:

Jika Menggunakan... Maka harus Memperhatikan... Alasannya
Time Based Filter Deadline QoS Jika Reader membatasi data masuk (misal: cuma mau 1 data per detik), pastikan Deadline-nya tidak lebih kecil dari 1 detik, atau sistem akan terus-terusan menganggap data terlambat.
Lifespan Durability Lifespan (masa kedaluwarsa) tidak akan terasa gunanya jika Durability-nya VOLATILE (langsung hilang). Lifespan sangat berguna pada data yang disimpan (TRANSIENT).
Reliability (RELIABLE) Resource Limits Pada mode RELIABLE, jika memori penuh (Resource Limits tercapai), Writer akan berhenti mengirim data sampai ada ruang kosong. Tanpa limit yang benar, aplikasi bisa freeze.
Entity Factory Operasi enable() Jika Factory disetel false (manual), entitas Anda tidak akan pernah mengirim/menerima data sampai Anda memanggil perintah .enable() di kode program.

Keterbatasan & Sintaks QoS pada Gateway (Node.js)

Berbeda dengan C++ yang memiliki akses penuh ke matriks puluhan kebijakan QoS OpenDDS, Gateway Node.js di proyek ini menggunakan bindings C++ (modul opendds) yang hanya mengekspos sebagian kecil konfigurasi QoS. Hal ini merupakan keterbatasan bawaan (limitation) dari library Node.js OpenDDS itu sendiri.

Keterbatasan Akses QoS

Di JavaScript/Node.js, Anda tidak bisa menyetel pengaturan lanjutan seperti Deadline, Liveliness, atau ukuran buffer Transport secara dinamis. Anda secara praktis hanya diizinkan untuk mendefinisikan tiga parameter dasar: Reliability, History, dan Durability. Jika Anda memaksa memasukkan properti lain yang tidak didukung ke dalam objek JSON QoS, modul tersebut akan mengabaikannya atau bahkan memicu Crash / Segmentation Fault pada Gateway.

Tabel Sintaks QoS di Node.js

Berikut adalah konfigurasi QoS utama yang aman dan didukung saat Anda menciptakan DataWriter atau DataReader di *Gateway* Node.js:

Jenis QoS Penulisan Sintaks JSON (Gateway) Penjelasan Praktis
Reliability reliability: { kind: 'RELIABLE_RELIABILITY_QOS' }

reliability: { kind: 'BEST_EFFORT_RELIABILITY_QOS' } 		Menentukan apakah Gateway menuntut jaminan pengiriman data. Wajib disesuaikan (*matching*) dengan QoS di C++. (Dalam proyek: Radar memakai BEST_EFFORT, sedangkan Command memakai RELIABLE).
History history: { kind: 'KEEP_LAST_HISTORY_QOS', depth: 10 }

history: { kind: 'KEEP_ALL_HISTORY_QOS' } 		Menentukan berapa banyak sampel data yang ditahan di *buffer* memori *Gateway*. Sangat disarankan memakai KEEP_LAST dengan depth kecil (misal: 1 atau 10) guna mencegah kebocoran memori (*memory leak*) pada server Node.js.
Durability durability: { kind: 'VOLATILE_DURABILITY_QOS' }

durability: { kind: 'TRANSIENT_LOCAL_DURABILITY_QOS' } 		Menentukan umur riwayat data. Jika diset TRANSIENT_LOCAL, Gateway/C++ bisa menerima pesan "terakhir" yang dikirim meskipun penerima baru saja menyala. (Proyek ini menggunakannya untuk menjamin penyelarasan sinkronisasi *Command*).

Contoh Format Objek QoS di server.js:

// Definisi QoS diubah menjadi objek JSON biasa
const qosObj = {
    DataWriterQos: {
        reliability: { kind: 'RELIABLE_RELIABILITY_QOS' },
        history: { kind: 'KEEP_LAST_HISTORY_QOS', depth: 10 },
        durability: { kind: 'TRANSIENT_LOCAL_DURABILITY_QOS' }
    }
};

// Disuntikkan sebagai argumen ketiga
const writer = participant.create_datawriter(topicName, typeName, qosObj);
