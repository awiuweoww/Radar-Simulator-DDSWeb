3. List QoS & Hirarki

Memahami kebijakan Quality of Service (QoS) untuk pengiriman data yang optimal.

QoS Matching: Kunci Komunikasi DDS

Dalam DDS, komunikasi antara publisher dan subscriber tidak akan langsung terjadi begitu saja, tetapi harus melalui proses QoS matching atau kecocokan QoS. Proses ini digunakan untuk memastikan bahwa konfigurasi Quality of Service yang dimiliki oleh publisher dan subscriber saling kompatibel sehingga pertukaran data dapat berlangsung dengan benar.

Jika QoS antara kedua pihak tidak sesuai, maka koneksi komunikasi dapat gagal terbentuk meskipun keduanya berada pada topic yang sama.

Daftar Kebijakan QoS Utama

  • Reliability: RELIABLE (jaminan sampai) vs BEST_EFFORT (cepat, tanpa jaminan).
  • Durability: VOLATILE (data transient) vs TRANSIENT_LOCAL (simpan data untuk subscriber baru).
  • History: KEEP_LAST (simpan N data terakhir) vs KEEP_ALL (simpan semua data).
  • Liveliness: Menentukan kapan sebuah entitas dianggap "mati" atau tidak aktif.
  • Deadline: Batas waktu pengiriman data harus sampai.

Hirarki Pewarisan QoS

QoS dapat diatur di berbagai level entitas. Jika tidak diatur, entitas di bawah akan mewarisi QoS dari entitas di atasnya:

  1. Domain Participant (Global)
  2. Publisher / Subscriber (Grup)
  3. DataWriter / DataReader (Spesifik/Individual)

Tabel Kompatibilitas QoS (Matching)

Tabel berikut merinci aturan kecocokan antara DataWriter (Offered) dan DataReader (Requested) agar komunikasi dapat terjalin:

Nama QoS Jika Writer Mengatur... Maka Reader Harus... Akibat Jika Tidak Cocok
Reliability Menyetel RELIABLE (Pasti sampai) Bisa meminta RELIABLE atau BEST_EFFORT. Jika Reader minta RELIABLE tapi Writer hanya sedia BEST_EFFORT, mereka tidak akan terhubung.
Durability Menyetel TRANSIENT (Simpan data lama) Bisa meminta TRANSIENT atau VOLATILE. Jika Reader minta data disimpan (TRANSIENT) tapi Writer tidak menyimpannya, mereka tidak akan terhubung.
Deadline Menyetel durasi 10 detik (Janji kirim tiap 10s) Harus meminta durasi sama atau lebih lama (misal 10s atau 12s). Jika Reader minta data tiap 5 detik tapi Writer hanya sanggup 10 detik, koneksi gagal.
Ownership Menyetel EXCLUSIVE (Hanya satu pengirim) Harus menyetel EXCLUSIVE juga. Jika satu SHARED dan satu EXCLUSIVE, mereka tidak akan saling bicara.
Liveliness Berjanji lapor diri tiap 5 detik Harus meminta laporan sama atau lebih lama (misal 5s atau 10s). Jika Reader ingin dipantau ketat tapi Writer santai, koneksi gagal.
Presentation Menyetel urutan tingkat GROUP Harus meminta tingkat yang sama atau lebih rendah (misal TOPIC atau INSTANCE). Jika Reader minta aturan lebih ketat dari yang disediakan Writer, data tidak akan mengalir.
Destination Order Menyetel SOURCE_TIMESTAMP Bisa meminta SOURCE atau RECEPTION. Jika Reader minta urutan waktu pengirim tapi Writer tidak menyediakannya, mereka tidak cocok.
Latency Budget Memberi info durasi pengiriman Nilai Writer harus lebih besar atau sama dengan nilai Reader. Digunakan untuk kecocokan asosiasi agar performa sistem tetap terpantau.

Tabel Ketergantungan (Inter-dependencies)

Beberapa kebijakan QoS saling mempengaruhi satu sama lain dalam operasionalnya:

Jika Menggunakan... Maka harus Memperhatikan... Alasannya
Time Based Filter Deadline QoS Jika Reader membatasi data masuk (misal: cuma mau 1 data per detik), pastikan Deadline-nya tidak lebih kecil dari 1 detik, atau sistem akan terus-terusan menganggap data terlambat.
Lifespan Durability Lifespan (masa kedaluwarsa) tidak akan terasa gunanya jika Durability-nya VOLATILE (langsung hilang). Lifespan sangat berguna pada data yang disimpan (TRANSIENT).
Reliability (RELIABLE) Resource Limits Pada mode RELIABLE, jika memori penuh (Resource Limits tercapai), Writer akan berhenti mengirim data sampai ada ruang kosong. Tanpa limit yang benar, aplikasi bisa freeze.
Entity Factory Operasi enable() Jika Factory disetel false (manual), entitas Anda tidak akan pernah mengirim/menerima data sampai Anda memanggil perintah .enable() di kode program.

Skenario Pengujian QoS

Berikut adalah skenario pengujian konkret untuk membuktikan efektivitas kebijakan QoS yang diterapkan dalam proyek ini (diambil dari materi presentasi dan ujicoba sistem):

1. Pengujian Durability (TRANSIENT_LOCAL)

Tujuan: Memastikan subscriber baru tetap menerima data terakhir yang dikirim sebelum subscriber tersebut aktif.

  • Langkah: Jalankan Gateway dan Frontend. Ubah Target Count menjadi 500 dari UI. Setelah itu, baru jalankan aplikasi C++ Backend.
  • Hasil: Begitu aplikasi C++ menyala, ia langsung menerima perintah 500 target tersebut karena data ditahan oleh Durability di Gateway.

2. Pengujian Reliability (Matching)

Tujuan: Memvalidasi mekanisme matching DDS dan penanganan silent fail pada Node.js.

  • Langkah: Sengaja buat kesalahan pengetikan (*typo*) pada JSON QoS di Node.js (misal: relability), sementara di C++ tetap RELIABLE.
  • Hasil: Terminal C++ akan memunculkan log peringatan sistem "Offered Incompatible QoS" (Ketidakcocokan QoS). Data tidak akan mengalir karena parameter antara Gateway dan Backend tidak sinkron.

3. Pengujian History (KEEP_LAST vs KEEP_ALL)

Tujuan: Membuktikan kontrol penggunaan memori (RAM) pada Gateway.

  • Langkah: Kirim data radar dengan kecepatan sangat tinggi (1000+ titik/detik). Bandingkan penggunaan RAM saat menggunakan KEEP_ALL vs KEEP_LAST (depth 1).
  • Hasil: Pada KEEP_ALL, RAM melonjak hingga crash. Pada KEEP_LAST, penggunaan RAM stabil meskipun dibombardir data.

4. Pengujian Lifespan

Tujuan: Memastikan data lama (stale) otomatis dibersihkan oleh sistem.

  • Langkah: Set Lifespan ke 3 detik. Hentikan pengiriman data dari C++ namun biarkan Frontend tetap terbuka.
  • Hasil: Setelah tepat 3 detik, data objek di peta akan otomatis hilang karena dianggap kedaluwarsa oleh mesin DDS.

5. Pengujian Liveliness (Heartbeat)

Tujuan: Mendeteksi kegagalan sistem secara otomatis.

  • Langkah: Hentikan proses C++ Backend secara paksa (*Kill Process*). Amati log pada Gateway.
  • Hasil: Dalam waktu maksimal 2 detik (Lease Duration), Gateway akan mendeteksi status "Liveliness Changed" dan mengetahui bahwa pengirim data telah mati.

6. Pengujian Integritas (Data Drop Detection)

Tujuan: Mengamati perilaku Best Effort saat sistem mencapai beban maksimal.

  • Langkah: Gunakan QoS Best Effort pada aliran radar. Tingkatkan jumlah target hingga 5.000+ objek. Buka konsol pengembang (F12) pada Frontend.
  • Hasil: RadarLogger pada Frontend akan memunculkan peringatan merah "DATA DROP DETECTED!". Hal ini membuktikan bahwa pada mode Best Effort, sampel data akan dikorbankan demi menjaga latensi tetap rendah (< 20ms) daripada memaksakan semua data terkirim tapi menyebabkan antrean (lag).

⚠️ Catatan Teknis: Penanganan "Silent Fail" pada Node.js

Salah satu kelemahan *binding* OpenDDS pada Node.js adalah sifatnya yang abaikan (*ignore*) terhadap kesalahan pengetikan (*typo*) pada kunci QoS. Jika kita menulis relability (kurang huruf 'i'), Node.js tidak akan memberikan error, melainkan diam-diam menggunakan nilai default DDS.

Solusi Implementasi: Untuk mengatasi hal ini, proyek ini menerapkan strategi "Warmup & Diagnostic Logging" melalui fungsi initializeDDS():

async function initializeDDS() {
    try {
        // 1. Load Pustaka IDL
        opendds.load(path.join(IDL_BIN_DIR, 'RadarTrack', 'libRadarTrack'));
        opendds.load(path.join(IDL_BIN_DIR, 'RadarCommand', 'libRadarCommand'));
        
        // 2. Jeda Inisialisasi (Discovery Gap)
        await new Promise(resolve => setTimeout(resolve, 3000));

        // 3. Verifikasi & Pemanasan (Warmup)
        const p0 = getParticipant(0);
        const writer = getWriter(p0, 'CommandTopic', 'RadarCommand::Command');
        
        if (writer) {
            console.log(' [DDS] DataWriter CommandTopic berhasil dibentuk.');
        }
    } catch (e) {
        console.error(' [Kesalahan DDS] Inisialisasi gagal:', e.message);
    }
}

Dengan memanggil fungsi ini saat *startup*, kita memaksa sistem melakukan pengecekan objek QoS sebelum ada permintaan dari user. Log [DDS] DataWriter ... berhasil dibentuk menjadi indikator utama bahwa konfigurasi JSON telah diterima dengan benar oleh engine biner OpenDDS.

Fleksibilitas & Sintaks QoS pada Gateway (Node.js)

Sebagai binding langsung dari C++, Gateway Node.js di proyek ini memiliki akses luas terhadap kebijakan QoS OpenDDS. Meskipun berjalan di lingkungan JavaScript, Anda dapat mengonfigurasi parameter krusial untuk menjamin performa dan keandalan data radar.

Dukungan Kebijakan QoS

Di Node.js, Anda dapat mendefinisikan berbagai kebijakan seperti Reliability, History, Durability, Lifespan, hingga Liveliness melalui objek JSON. Hal terpenting adalah memastikan pengetikan kunci (key) dan nilai (value) sesuai dengan standar biner OpenDDS guna menghindari perilaku Silent Fail atau kegagalan inisialisasi entitas.

Tabel Sintaks QoS di Node.js

Berikut adalah konfigurasi QoS utama yang aman dan didukung saat Anda menciptakan DataWriter atau DataReader di *Gateway* Node.js:

Jenis QoS Penulisan Sintaks JSON (Gateway) Penjelasan Praktis
Reliability reliability: { kind: 'RELIABLE_RELIABILITY_QOS' }

reliability: { kind: 'BEST_EFFORT_RELIABILITY_QOS' } 		Menentukan apakah Gateway menuntut jaminan pengiriman data. Wajib disesuaikan (*matching*) dengan QoS di C++.
History history: { kind: 'KEEP_LAST_HISTORY_QOS', depth: 10 }

history: { kind: 'KEEP_ALL_HISTORY_QOS' } 		Menentukan berapa banyak sampel data yang ditahan di *buffer* memori *Gateway*. Sangat disarankan memakai KEEP_LAST guna mencegah *memory leak*.
Durability durability: { kind: 'VOLATILE_DURABILITY_QOS' }

durability: { kind: 'TRANSIENT_LOCAL_DURABILITY_QOS' } 		Menentukan umur riwayat data. TRANSIENT_LOCAL memungkinkan pengiriman data terakhir kepada subscriber yang baru bergabung.
Lifespan lifespan: { duration: { sec: 3, nanosec: 0 } } Mengatur masa kedaluwarsa data. Setelah waktu terlampaui, data akan otomatis dihapus dari cache subscriber.
Liveliness liveliness: { kind: 'AUTOMATIC_LIVELINESS_QOS', lease_duration: { sec: 2, nanosec: 0 } } Mengatur deteksi "detak jantung" (*heartbeat*). Jika dalam waktu tertentu tidak ada kabar, entitas dianggap mati.
Deadline deadline: { period: { sec: 1, nanosec: 0 } } Kebijakan yang menuntut pengiriman data dalam interval waktu tertentu. Jika meleset, sistem akan memicu peringatan.
Ownership ownership: { kind: 'EXCLUSIVE_OWNERSHIP_QOS' }

ownership: { kind: 'SHARED_OWNERSHIP_QOS' } 		Mengatur apakah satu *topic* hanya boleh ditulis oleh satu *writer* utama (Exclusive) atau berbagi (Shared).

Contoh Format Objek QoS di server.js:

// Definisi QoS di Node.js (Format FLAT - Tanpa pembungkus DataWriterQos)
const qosObj = {
    reliability: { kind: 'RELIABLE_RELIABILITY_QOS' },
    history: { kind: 'KEEP_LAST_HISTORY_QOS', depth: 10 },
    durability: { kind: 'TRANSIENT_LOCAL_DURABILITY_QOS' }
};

// Disuntikkan sebagai argumen ketiga
const writer = participant.create_datawriter(topicName, typeName, qosObj);

Pemetaan QoS: Web ke DDS

Penting untuk dipahami bahwa protokol Web (HTTP/WebSocket) tidak mendukung kebijakan QoS DDS secara asli. Berikut adalah bagaimana strategi QoS diterapkan di setiap lapisan:

Lapisan Protokol Karakteristik QoS
Frontend (React) HTTP / WS (TCP) Implicit: Hanya mengandalkan keandalan TCP. Tidak ada kontrol Durability atau Liveliness di level protokol browser.
Gateway (Node.js) Bridge / Proxy The Translator: Mengambil paket JSON dari Web dan membungkusnya ke dalam entitas DDS yang memiliki QoS lengkap.
Backend (C++) RTPS (UDP) Full Native QoS: Menggunakan seluruh spektrum kebijakan QoS OpenDDS untuk manajemen data tingkat tinggi.

Kesimpulan: React tidak menyetel QoS, ia "menikmati" manfaat QoS yang dikonfigurasi di Gateway. Misalnya, jika Gateway disetel TRANSIENT_LOCAL, React akan otomatis menerima data terakhir saat terkoneksi ke WebSocket tanpa perlu meminta ulang (request) secara manual.
