Setup & Instalasi

Backend simulator radar dibangun menggunakan OpenDDS murni dengan bahasa C++. Untuk memastikan kebebasan dependensi, alur kompilasi (build) sangat direkomendasikan menggunakan Conan sebagai package manager (seperti yang dijabarkan pada tahapan Dockerfile).

# 1. Pastikan dependensi OS, Python (pip), dan CMake (>= 3.31) sudah terinstal.
# 2. Unduh dan Ekstrak OpenDDS (v3.29.1)
wget https://docs.len-iot.id/s/xm9zTrTASaBxd8p/download/OpenDDS-3.29.1.zip
unzip OpenDDS-3.29.1.zip -d /opt/OpenDDS

# 3. Setup Environment Variable OpenDDS (Penting)
export ACE_ROOT="/opt/OpenDDS/ACE_wrappers"
export TAO_ROOT="/opt/OpenDDS/ACE_wrappers/TAO"
export DDS_ROOT="/opt/OpenDDS"
export MPC_ROOT="/opt/OpenDDS/ACE_wrappers/MPC"
export LD_LIBRARY_PATH="/opt/OpenDDS/ACE_wrappers/lib:/opt/OpenDDS/lib:$LD_LIBRARY_PATH"
export PATH="/opt/OpenDDS/ACE_wrappers/bin:/opt/OpenDDS/bin:$PATH"

# 4. Masuk ke root backend & Inisialisasi Conan
cd be-stream-odds-cpp
pip3 install conan
conan profile detect --force
conan install . --output-folder=build --build=missing

# 5. Build menggunakan CMake (Membaca preset dari Conan)
cmake --preset conan-release
cmake --build build --config Release --target all -j$(nproc)

# 6. Menjalankan Binary Backend
cd build
./be-stream-odds-cpp -DCPSConfigFile ../rtps.ini

Penjelasan Detail Core Konfigurasi & Engine

Berikut ini adalah tiga file krusial yang mengatur berjalannya simulator radar di backend:

1. Engine Utama: src/app.cpp

File *entry point* di mana *loop* simulasi berjalan. Tiga tugas utamanya:

  • Thread Terpisah: Memisahkan proses baca perintah (*subscriber*) ke latar belakang agar pengiriman data tidak terhambat.
  • Pre-calculation: Menghitung nilai rumit (sin/cos/heading) untuk 10.000 target sebelum *loop* dimulai guna menghemat beban CPU.
  • Loop Simulasi (200ms): Terus berputar menghitung posisi/trajektori baru dan mem-publish datanya ke DDS.
2. Konfigurasi Jaringan: rtps.ini

File wajib yang di-*load* lewat flag -DCPSConfigFile untuk mengatur koneksi *low-level* OpenDDS:

  • DCPSDefaultDiscovery=rtps: Memaksa DDS memakai sistem Peer-to-Peer (*multicast*) tanpa *server* sentral.
  • transport_type=rtps_udp: Mengirim lalu lintas paket data via UDP untuk mengejar latensi rendah.
  • Buffer Maksimal: Memperbesar rcv_buffer_size & snd_buffer_size OS agar sanggup menahan ribuan paket per detik tanpa *drop*.
3. Fallback Discovery: simple.ior

File warisan dari sistem DDS terpusat (berbasis CORBA InfoRepo).

  • Isi File: Berupa string heksadesimal yang menyimpan alamat IP & Port server DCPSInfoRepo.
  • Fungsi: Bertindak layaknya Buku Telepon agar *publisher* dan *subscriber* saling menemukan.
  • Konteks: Karena sekarang kita memakai P2P murni (rtps.ini), file ini hanya dibiarkan sebagai mekanisme fallback jika sewaktu-waktu beralih kembali ke arsitektur sentral.

Bagaimana mengatur Pub, Sub, Domain, Domain Participant dan Topic di OpenDDS

Implementasi C++ murni OpenDDS di backend sangat berpegang pada standar spesifikasi Data Distribution Service (DDS) dari OMG. Konsep dasar mengenai apa itu Domain Participant, Topic, Publisher, maupun Subscriber dapat Anda baca secara menyeluruh di bab Dasar Teori.

Alur Implementasi Nyata di Project

Dalam proyek ini, kerumitan inisialisasi entitas DDS tidak diletakkan bertumpuk di satu file main, melainkan diabstraksi ke dalam arsitektur berbasis OOP (Abstract & Concrete classes). Berikut adalah penjabaran flow penciptaan entitas DDS beserta file aslinya:


1. Entry Point: app.cpp src/app.cpp (Line 30 - 37)

Aplikasi dimulai dengan memanggil Participant Factory bawaan OpenDDS, lalu mem-passing factory ini kepada objek Singleton ODDSDomainParticipant. Setelah participant berhasil dibuat, ia disuntikkan ke kelas Publisher dan Subscriber konkret.

// Inisialisasi Domain Participant
DDS::DomainParticipantFactory_var factory = TheParticipantFactoryWithArgs(argc, argv);
auto participant = ODDSDomainParticipant::get_instance(factory)->get_participant_();

// Menyuntikkan Participant ke Publisher & Subscriber
RadarTrackODDSPublisher radar_publisher(participant);
RadarCommandODDSSubscriber radar_subscriber(participant);
2. Implementasi Domain Participant src/adapters/.../domain_participant.cpp (Line 50)

File ini menangani inisialisasi Domain Participant pada domain ID spesifik (default: 0). Jika file konfigurasi transport RTPS tidak diberikan melalui argumen CLI, adapter ini memuat rtps.ini lokal secara otomatis sebagai fallback.

participant_ = factory->create_participant(domain, PARTICIPANT_QOS_DEFAULT, nullptr, OpenDDS::DCPS::DEFAULT_STATUS_MASK);
3. Abstraksi Publisher & Subscriber Base abstract_odds_publisher.cpp & abstract_odds_subscriber.cpp

Kelas abstrak ini bertugas mengeksekusi create_publisher() dan create_subscriber(). Di sinilah QoS diinisialisasi secara aman menggunakan get_default_publisher_qos() agar meminimalisir kemungkinan segmentation fault akibat manipulasi QoS langsung.

4. Concrete Publisher (RadarTrack) src/adapters/.../radar_track_publisher.cpp (Line 17 - 32)

Berbeda dengan JS di frontend yang sangat dinamis, C++ mewajibkan registrasi TypeSupport sebelum Topic bisa dibuat. File ini memuat struktur IDL RadarTrack, mengatur QoS (Best Effort, Lifespan 3 detik), memanggil pembuatan Topic RadarTrackTopic, lalu melakukan konversi narrowing menjadi objek tipe aman TrackDataDataWriter.

// 1. Registrasi TypeSupport
type_support = std::make_unique<RadarTrack::TrackDataTypeSupportImpl>().release();
type_name = type_support->get_type_name();
result = type_support->register_type(*this->get_participant_(), type_name);

// 2. Modifikasi QoS & Set Topic
this->get_w_qos_()->lifespan.duration.sec = 3;
this->set_topic(type_name, "RadarTrackTopic", writer);

// 3. DataWriter Narrowing
radar_writer_ = RadarTrack::TrackDataDataWriter::_narrow(writer);
5. Eksekusi Pengiriman Data (Publish / Write) src/adapters/.../radar_track_publisher.cpp (Line 38 - 54)

Setelah diinisialisasi, proses pengiriman data dilakukan dengan memuat nilai ke dalam objek tipe bentukan IDL (RadarTrack::TrackData), lalu memanggil method write() pada objek DataWriter yang sudah di-narrow.

// 1. Memuat data ke objek IDL C++
radar_msg_.trackId = data.trackId;
radar_msg_.lat = data.lat;
radar_msg_.lon = data.lon;

// 2. Menulis / Mengirim data ke DDS Domain
DDS::ReturnCode_t result = radar_writer_->write(radar_msg_, DDS::HANDLE_NIL);
this->get_odds_operator_()->check_status(result, "radar_writer_->write() failed");
6. Concrete Subscriber (RadarCommand) src/adapters/.../radar_command_subscriber.cpp (Line 23 - 27)

Prosedur serupa terjadi untuk penerima kendali (Command). Tipe dukungan didaftarkan, QoS dimodifikasi menjadi RELIABLE (karena instruksi tidak boleh hilang), dan Topic diset ke CommandTopic, lalu diakhiri dengan narrowing CommandDataReader.

this->get_r_qos_()->reliability.kind = DDS::RELIABLE_RELIABILITY_QOS;
this->set_topic(type_name, "CommandTopic", reader);
radar_command_reader_ = RadarCommand::CommandDataReader::_narrow(reader);
7. Eksekusi Penerimaan Data (Subscribe / Take) src/adapters/.../radar_command_subscriber.cpp (Line 32 - 68)

Pengambilan data diimplementasikan di dalam loop thread menggunakan method take(). Data diekstrak dengan memvalidasi info_seq_, dan wajib diakhiri dengan return_loan() untuk mengembalikan kepemilikan memori ke OpenDDS.

// 1. Mengambil (take) data dari queue DDS
this->result_ = this->radar_command_reader_->take(
    this->msg_list_, this->info_seq_, DDS::LENGTH_UNLIMITED,
    DDS::ANY_SAMPLE_STATE, DDS::ANY_VIEW_STATE, DDS::ANY_INSTANCE_STATE
);

if (this->result_ == DDS::RETCODE_OK) {
    // 2. Iterasi & Ekstrak Data Valid
    for (CORBA::ULong i = 0; i < this->msg_list_.length(); i++) {
        if (this->info_seq_[i].valid_data) {
            this->command_receive_data_.action = this->msg_list_[i].action.in();
            this->command_receive_data_.value = this->msg_list_[i].value;
        }
    }
    // 3. Mengembalikan "pinjaman" memori ke OpenDDS
    this->radar_command_reader_->return_loan(this->msg_list_, this->info_seq_);
}

Prasyarat Krusial OpenDDS C++

  • DDS::ReturnCode_t Checking: Hampir setiap operasi OpenDDS mengembalikan kode status. Proyek ini membungkusnya dalam utilitas odds_operator_.check_status() untuk memastikan jika gagal (seperti memori penuh atau IDL tidak cocok), aplikasi akan dihentikan secara graceful dengan log error.
  • TypeSupport Registration: Pendaftaran tipe ini adalah langkah wajib compiler C++. Tanpa mendaftarkan instansiasi TypeSupportImpl, eksekusi create_topic() pasti gagal.
  • Sistem CORBA Smart Pointer (_var): Penanganan struktur atau objek DDS secara internal menggunakan _var (seperti DDS::Topic_var). Penggunaan pointer mentah sangat dilarang demi mencegah memori leak.

Bagaimana mengatur QoS di OpenDDS pada BE

Dalam spesifikasi DDS, Quality of Service (QoS) secara teori dapat dipasang di berbagai level hierarki (DomainParticipant, Publisher/Subscriber, Topic, maupun DataWriter/DataReader). Namun, di dalam arsitektur backend ini, pengaturan QoS secara spesifik difokuskan dan diterapkan pada level End-Point, yaitu pada objek DataWriter dan DataReader.

Mengapa QoS diterapkan di level DataWriter dan DataReader?

  • Publisher & Subscriber: Berfungsi sebagai "manajer grup" dari writer/reader. Memberikan QoS di level ini biasanya ditujukan untuk *group presentation* atau berbagi memori, namun tidak secara spesifik mengatur perilaku paket datanya.
  • Topic: Berfungsi sebagai penghubung nama dan TypeSupport. Meskipun *Topic* memiliki konfigurasi QoS bawaan, nilainya seringkali hanya dipakai sebagai kerangka dasar (*baseline*) lalu ditimpa (*override*) oleh entitas pengirim/penerima aslinya.
  • DataWriter & DataReader: Inilah objek "pekerja keras" riil yang melakukan I/O *byte* ke jaringan. Dengan menyematkan QoS seperti RELIABILITY atau LIFESPAN langsung pada entitas ini, kita memperoleh kontrol 100% presisi untuk setiap aliran data tanpa mengganggu jalur *publisher/subscriber* lain.
Penerapan di Sisi Pengirim (DataWriter) src/adapters/.../radar_track_publisher.cpp (Line 22 - 32)

Pada saat inisialisasi RadarTrackODDSPublisher, sistem mengambil nilai default variabel w_qos_ (Writer QoS), memodifikasinya menjadi Best Effort (untuk *streaming* latensi rendah), dan menyematkan Lifespan 3 detik agar data basi otomatis terbuang.

// 1. Modifikasi parameter Writer QoS (Line 22-29)
this->get_w_qos_()->reliability.kind = DDS::BEST_EFFORT_RELIABILITY_QOS;
this->get_w_qos_()->lifespan.duration.sec = 3;
this->get_w_qos_()->liveliness.kind = DDS::AUTOMATIC_LIVELINESS_QOS;

// 2. Injeksi QoS saat penciptaan DataWriter (dipanggil via set_topic pada Line 31)
this->set_topic(type_name, "RadarTrackTopic", writer);
Penerapan di Sisi Penerima (DataReader) src/adapters/.../radar_command_subscriber.cpp (Line 22 - 24)

Pola identik diterapkan pada RadarCommandODDSSubscriber. Nilai r_qos_ (Reader QoS) diubah mutlak menjadi RELIABLE (karena perintah kendali Start/Stop dari frontend pantang hilang di jalan) sebelum disematkan ke pembuatan DataReader.

// 1. Modifikasi parameter Reader QoS (Line 23)
this->get_r_qos_()->reliability.kind = DDS::RELIABLE_RELIABILITY_QOS;

// 2. Injeksi QoS saat penciptaan DataReader (dipanggil via set_topic pada Line 24)
this->set_topic(type_name, "CommandTopic", reader);

⚠️ Peringatan: Bahaya Segmentation Fault pada C++ QoS

Dalam bahasa C++, ketika Anda membuat variabel QoS baru (misalnya DDS::DataWriterQos my_qos;), isinya awalnya adalah "sampah memori" (garbage values) yang tidak valid. Jika Anda hanya mengubah parameter reliability dan membiarkan parameter lainnya berisi nilai sampah, aplikasi OpenDDS akan crash (segmentation fault) saat membaca nilai sampah tersebut.

Solusinya: Di dalam backend ini (pada file abstract), kita selalu memanggil fungsi get_default_datawriter_qos() terlebih dahulu untuk mengisi struktur tersebut dengan nilai bawaan yang aman. Setelah memori struktur tersebut aman, barulah kita modifikasi nilai spesifik yang kita mau.

Bagaimana mengatur dan mengkompilasi IDL di C++ (Backend)

Berbeda dengan Node.js/JavaScript yang dapat memecah skema IDL secara dinamis (*runtime*), di bahasa C++, file IDL tidak bisa langsung dijalankan. Skema IDL tersebut harus dikonversi terlebih dahulu menjadi puluhan file *header* (.h) dan *source* (.cpp) C++ agar kompilator (GCC/Clang) dapat mengenalinya sebagai *Class/Struct* yang sah.

1. Kompilasi IDL menggunakan generate_idl be-stream-odds-cpp/generate_idl

Di direktori dasar *backend*, terdapat *script* bernama generate_idl. Jika Anda merubah rancangan struktur data di dalam idl/RadarTrack/RadarTrack.idl, Anda diwajibkan untuk membangkitkan ulang kodenya melalui terminal menggunakan eksekusi skrip ini (contoh: ./generate_idl idl/RadarTrack/RadarTrack).

#!/bin/bash

# Validasi argumen terminal
if [ "$#" -lt 1 ]; then
    echo "Usage: $0 <FILE_NAME>"
    exit 1
fi

IDL_FILE_NAME="$1.idl"
TYPE_SUPPORT_FILE_NAME="$1TypeSupport.idl"

# 1. tao_idl: Menciptakan C++ CORBA bindings
tao_idl -I "$DDS_ROOT" -Sa -St -Sm -Sci -in --idl-version 4 --unknown-annotations ignore "$IDL_FILE_NAME"

# 2. opendds_idl: Menghasilkan struktur DDS TypeSupport
opendds_idl -Gxtypes-complete "$IDL_FILE_NAME"

# 3. tao_idl (Tahap 2): Mengkompilasi TypeSupport ke C++
tao_idl -I "$DDS_ROOT" -Sa -St -Sm -Sci -in --idl-version 4 --unknown-annotations ignore "$TYPE_SUPPORT_FILE_NAME"

echo "Execution completed."
2. Hasil Kompilasi & Penempatan (*Models*) src/models/odds_models/... & CMakeLists.txt (Line 25-34)

Satu file IDL akan meledak menjadi sekitar 11 file C++ setelah dikompilasi (misalnya: RadarTrackC.cpp, RadarTrackS.h, RadarTrackTypeSupportImpl.cpp, dll).

  • Penempatan: Pindahkan kesebelas file hasil generate tersebut ke dalam folder *models* yang relevan (contoh: src/models/odds_models/radar_track_model/).
  • Kompilasi Akhir: Anda tidak perlu mendaftarkannya satu persatu. File CMakeLists.txt sudah didesain memindai seluruh .cpp di folder *models* tersebut secara otomatis.
# Potongan kode di CMakeLists.txt yang memindai otomatis
file(GLOB_RECURSE SOURCES 
    src/*.cpp 
    src/*.cc 
    src/*.h 
    src/*.hpp
)
# Memasukkan semua file TypeSupport dan logic ke dalam objek kompilasi
add_library(shared-objects OBJECT ${SOURCES})
add_executable(${PROJECT_NAME} src/app.cpp $)
